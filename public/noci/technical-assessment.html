2. Executive summary

The system is substantially more built than a proof of concept. It is a real headless commerce application — 164 API routes, 64 database models, 51 migrations, 8,056 tests, a live Shopify integration, and a money-safety layer around paid AI generation. The typecheck is clean. The architecture has a deliberate and well-executed fail-open design on the shopper path.

It is not yet production-shaped as an engineering operation. The gaps are concentrated in process and custody rather than in the code itself:

  • No CI exists. This is not theoretical: six test failures introduced in the last three weeks are sitting in main undetected (F-02).
  • No production error monitoring is wired, and 293 ad-hoc log calls bypass the well-built monitoring seam that does exist. A fail-open system without observability fails invisibly (F-10).
  • No backup or restore posture, and no restore drill (F-04) — and we now know schema-first recovery would fail: prisma migrate deploy cannot rebuild the database from its own migration history, which is the documented, checklisted production workflow (F-23).
  • First Load JS is 406–502 kB gzipped on shopper routes because the committed catalog and taxonomy data are bundled into client JavaScript (F-24).
  • A single shared password guards the entire back office, with no actor attribution (F-05) — and the token derived from it is a non-revocable bearer credential, on a login endpoint with no rate limit (F-17).
  • The manufacturer source data the client's own handover calls its "single biggest data-loss risk" is not in the delivered checkout (F-03).
  • Account deletion reaches 2 of 9 personal-data stores, Shopify's customers/redact webhook is not handled, and no store has a retention limit (F-21, F-22).
  • The consent banner does not bind the server. soc_consent is read in exactly one place — the client component — so the server-side conversion relay transmits hashed email and phone to Meta and TikTok on every purchase regardless of the shopper's choice, contradicting the banner's own copy . Free to fix today because the relay is still inert; an incident once the CAPI tokens are set.
  • A prior internal readiness review (July 2026) confirmed 45 findings — 9 blockers, 36 must-fix. Now audited: all 9 blockers are closed and at least 21 of 36 must-fixes, but 9 remain open — and four of those are findings this assessment reached independently (F-08).
  • The async pipelines run on a hand-rolled Postgres queue with no depth observability, no global concurrency bound, and a documented collision with a Vercel platform guard (F-12) — while the Looks lane simultaneously permits only one rendering set across the whole back office (F-26). Unbounded cost concurrency, zero throughput concurrency.
  • A five-second Neon stall serves shoppers an archived catalog and 404s the live product line. The fail-open floor is a legitimate design, but the snapshot it falls back to is 20 days old and describes the archived prototype range — so during a stall, PDPs for real, purchasable products return hard 404s, silently (F-16, escalated to HIGH on August 2026). The one-hour fix — regenerate the snapshot — removes the payload even before the mechanism is touched.
  • Merchandising taxonomy is not data — it is committed source code. ~1.4 MB of generated TypeScript holds the facet, pattern and colour tags the storefront navigates by. Changing them requires an engineer, a local script run, a commit and a redeploy (F-15).

A framing correction worth making early, because it changes how several findings should be read. The catalog data tier (F-15, F-16, F-24) looks like odd architecture and is better understood as an unfinished internal migration — see §4d. The commerce backend was built correctly and in one day: the PoC's hardcoded catalog was pushed into Shopify, Neon has only ever held a mirror, and the runtime database read seam shipped five days later. What was never retired is the compatibility shim that let 120 existing import sites keep working, and 69 of them still read it. "Finish the migration you started" is both the accurate description and a far more actionable one than "rearchitect your data tier."

The dominant pattern, and the one worth naming early: this codebase has exceptional institutional memory and almost no enforcement. next.config.ts and lib/marketing/video/finish.ts are annotated incident ledgers, with dates and deployment IDs. Somebody learned each lesson the hard way and wrote it down. But nothing executes those lessons — no CI, no pre-merge gate, no platform-parity check. Knowledge sits in prose that a future engineer must read and remember. Converting the best of that prose into automated gates is the highest-leverage, lowest-cost change available.

F-04

No backup or restore posture

HIGHEVIDENCED+

There is no backup strategy in the repository. The handover marks Neon's point-in-time restore as "the assumed safety net [inferred — not configured anywhere in the repo]" and states that establishing an explicit posture and running a restore drill is an early task.

One related item is worth calling out: Event_purchase_order_key is a raw-SQL partial unique index (purchase idempotency) that Prisma cannot see. prisma migrate diff will propose dropping it. A restore or schema-sync performed by someone unaware of this would silently remove purchase idempotency.

Recommendation: confirm Neon PITR retention, document the restore procedure, and rehearse it against a branch before launch.

F-05

Single shared admin credential, no actor attribution

HIGHEVIDENCED+

ADMIN_PASSWORD (92 references) is one shared secret protecting the entire back office — including every paid-generation path and all catalog and pricing writes. There are no user accounts, no roles, and no per-actor audit trail.

The session scheme is sessionToken = SHA-256("society-admin:" + password) (lib/merch/auth.ts), used as a bearer value in the admin_session cookie or the x-internal-auth header. It is unsalted, not stretched, has no expiry and no rotation mechanism; the cookie value is a deterministic function of a static password.

To the team's credit the model does fail closed in production, and a per-route requireAdmin gate now backs the proxy (lib/merch/guard.ts) — a previously identified gap they closed.

The prior internal review reached the same conclusion independently: "One shared admin credential for every verb, and no actor attribution anywhere — the trust ladder cannot be enforced or audited."

Recommendation: for a team larger than one operator this needs real accounts before production. At minimum, per-actor identity on every mutating admin route.

F-06

The ffmpeg binary selection is an install-time race (Ad Studio video)

MEDIUMVERIFIED locally, UNCONFIRMED in production+

Verified on this machine:

  • ffmpeg-static@5.3.0 resolves to a johnvansickle 7.0.2 static build with 494 filters and no drawtext. Direct probe: No such filter: 'drawtext'.
  • lib/marketing/video/finish.ts uses drawtext 31 times — it is the entire text and card layer of the Ad Studio finisher.
  • Result: the four video-finisher integration tests fail.

The repository already knows this. finish.ts:1427-1434 documents the exact cause ("since FFmpeg 6.1, drawtext requires libharfbuzz — ffmpeg-static's linux builds AND johnvansickle release builds ship WITHOUT it") and ships a fix: a sha256-pinned BtbN build fetched from their own Vercel Blob store into /tmp.

The hazard is the ordering in resolveFfmpegBinary() (finish.ts:1389-1413):

override → FFMPEG_PATH → ffmpeg-static → BtbN fallback

The working binary is last. It engages only when ffmpeg-static's binary is absent. Two other mechanisms push the opposite way:

  1. pnpm-workspace.yaml lists ffmpeg-static under onlyBuiltDependencies specifically so its postinstall does download the binary.
  2. next.config.ts explicitly traces that binary into the /api/cron/creative-drain lambda.

So whether production video finishing works depends on whether the Vercel builder's postinstall download succeeded. If it succeeded, the drawtext-less binary shadows the good one. The comment at finish.ts:1418 records that Vercel's install did skip it on July 2026 — which is precisely what makes the fallback engage today.

This is a correctness outcome resting on an install-time accident.

Recommendation: verify against production first — look for [finish] runtime ffmpeg fallback engaged in the creative-drain logs. Then make the selection explicit: probe for drawtext before accepting a binary, rather than trusting resolution order.

F-10

Observability: 293 ad-hoc log calls bypass a well-built monitoring seam, and no off-box transport is wired

HIGHVERIFIED+

Using console.* is not itself the problem. On Vercel there is no filesystem to write to and no long-lived process to host a logging daemon; the platform captures a function's stdout/stderr. console.* is the correct, idiomatic primitive for Next.js on Vercel, and heavyweight loggers (pino, winston) add little in a lambda. The scale and the structure are what matter.

Measured across app/, lib/, components/ excluding tests: 293 call sites in 125 files — 184 console.error, 62 console.warn, 59 console.log.

The codebase has a genuinely well-built monitoring seam, lib/monitoring/report.ts: per-call env reads, bounded payloads, a 4-second webhook timeout, a hard never-throw invariant, and one shared event shape for client and server. Exactly two things call it — instrumentation.ts (onRequestError) and app/api/monitoring/client-error/route.ts. The other 293 sites do not.

That gap matters more here than it would elsewhere, because of the deliberate fail-open design. onRequestError only fires for errors that escape to the Next server. This codebase catches aggressively and returns success on purpose — app/api/shopify/webhooks/route.ts is the textbook case, swallowing everything post-HMAC and always returning 200 to avoid a Shopify retry storm. That is the right call. But it means the caught error reaches onRequestError never, so it reaches reportServerError never, so it reaches an external monitor never. Its only traces are a console line and, in that route's case, a SyncRun audit row.

A fail-open system without observability does not fail gracefully — it fails invisibly.

Compounding issues:

  1. No off-box transport is wired. ERROR_WEBHOOK_URL is unset as far as the repository shows, so the fallback (a [monitor] {…} console line) is the durable record. Vercel runtime logs are short-retention without a Log Drain, so most error evidence likely evaporates. The client's own onboarding checklist item #6 is "Wire ERROR_WEBHOOK_URL to something your team watches", and the go-live checklist item "Set a monitoring transport" is unchecked.
  2. SENTRY_DSN is a trap for the incoming team. It is read per-call and surfaced in the log line, but no @sentry SDK ships (zero matches in package.json). Setting the DSN in Vercel changes nothing. The code and launch-handoff.md §2.9 both say so honestly — but only if you read them first.
  3. No no-console ESLint rule (eslint.config.mjs is stock next/core-web-vitals + typescript), so nothing prevents the two systems from diverging further.

Positives worth recording. Log hygiene is good: a scan for PII and secrets in log statements found no emails, phone numbers, addresses, tokens, API keys or secrets — only internal customer IDs in two lib/taste/recompute.ts lines. Messages carry consistent [subsystem] prefixes, so logs are greppable. And the file that prompted this review, app/api/shopify/webhooks/route.ts, is one of the better examples: HMAC-first, deliberate always-200 semantics, and a SyncRun database row backing the console line.

Recommendation, in order: (1) set ERROR_WEBHOOK_URL before go-live — it is a single environment variable and it is the difference between having and not having production error visibility; (2) route caught-and-swallowed errors on money and commerce paths through reportServerError rather than bare console.error; (3) either install the Sentry SDK or remove the SENTRY_DSN flag so it cannot mislead; (4) add a no-console lint rule with an allowlist for the monitoring module.

HIGHVERIFIED+

Is there a queue? Yes — but not a queue product. There is no queue library in package.json (no Inngest, BullMQ, QStash, Trigger.dev, Temporal, SQS, Pub/Sub). What exists is a hand-rolled Postgres-backed job queue, and it is a legitimate implementation of the pattern:

Element How it works
Work store Rows in Postgres (BatchItem, GeneratedLook, CreativeJob) with status + leasedAt
Claim Conditional UPDATE … WHERE status=PENDING AND (leasedAt IS NULL OR leasedAt < staleBefore) — a real compare-and-swap, so two invocations cannot claim the same row (lib/marketing/studio.ts:3240)
Lease LEASE_MS = 20 min, reclaimed when stale
Unit of work One bounded item per invocation
Continuation HTTP self-kick — the route fetches itself via waitUntil while work remains
Backstop Per-minute cron heartbeat re-claims stale leases
Poison handling Per-item parked / failed status with a reason — an effective dead-letter lane

Leases now cover the fill lanes too (styled-fill, colorway-fill), closing a finding from the client's own July 2026 review. The self-kick is correctly gated on real progress to avoid hot-looping on fully-leased work.

Will long-running jobs choke the web tier?

Not through CPU or process contention. On Vercel each route compiles to its own function with its own instances, so an 800-second ffmpeg encode in /api/cron/creative-drain shares no process with /product/[id]. The storefront is additionally well insulated: ISR revalidate = 300 on /, PDP and /occasion/[id], s-maxage edge caching on the public APIs, a single tag-cached getCatalog() read with a 5-second timeout race, and fail-open to the build-time snapshot. That is genuinely good design and should be credited.

Contention is real on four shared channels, none of which are CPU:

1. Neon connection pool — the highest-probability bottleneck. Every concurrent lambda holds Prisma connections; 11 routes declare maxDuration = 800, so a single invocation can hold connections for over 13 minutes. Drawing on one pool simultaneously: four per-minute crons, their self-kick chains, two */10 fill crons, and all dynamic storefront traffic. The client's own launch-handoff §5 lists "Neon connection-pool ceiling" as untested load-test item #1.

The compounding risk is the interaction with the fail-open design. If the pool exhausts, storefront reads fail their timeout race and silently fall back to the build-time catalog snapshot — the site keeps serving, but stale, with no error surfaced. Combined with F-10 (no monitoring transport wired), a connection-pool exhaustion event would be invisible: no 5xx, no alert, just a quietly frozen catalog.

2. Vercel's invocation-chain loop detector — already hit in production. lib/looks-creator/assets.ts:53-57 documents it verbatim:

"Vercel threads the invocation chain into same-deployment fetches; by the 3rd-4th self-kicked drain of a wave that chain trips INFINITE_LOOP_DETECTED and a plain static-asset request 508s (July 2026: corset o'clock's afterparty-jean flat 508'd in the lambda while serving 200 publicly)."

The fix applied was to fetch assets with Node's raw HTTP client instead of the runtime-patched global fetch, bypassing chain propagation. But the self-kick itself still uses global fetch (app/api/cron/looks-drain/route.ts:41), so chain depth continues to accumulate along the kick path. The continuation architecture is in standing tension with a platform guard; the symptom class has already caused one live incident.

3. Account-level function concurrency. Eleven 800-second routes plus self-kicking chains can hold many long-lived instances at once. Vercel enforces plan-level concurrency; exhausting it queues all functions — including the genuinely dynamic storefront paths (/shop, and /api/checkout, which is uncacheable and Shopify-bound).

4. Cron thundering herd. Four crons fire every minute simultaneously (intake-drain, looks-drain, creative-drain, merchant-council), each spawning its own kick chain; shopify-reconcile and brain-synthesis both fire at 09:00; the two fill crons share */10. There is no jitter or stagger.

What the hand-rolled queue is missing versus a managed one

  • No queue-depth or lease-age metric, and no alerting. Backlog is visible only by opening the relevant admin desk. Nothing detects "the drain has been stuck for two hours." Directly compounds F-10.

  • No global concurrency bound. Each lane self-kicks independently; nothing caps total simultaneous paid work across lanes. This mirrors the spend finding in the client's own review — "all spend caps are per-kind/per-lane silos with no global daily circuit breaker."

    Read this together with F-26, which looks like its opposite and is not. The Looks lane enforces a hard global lock of exactly one rendering set across the entire admin surface. The two statements are about different axes: cost concurrency is unbounded, throughput concurrency is bounded at one. That is the worst available pairing, and neither half is a trade-off anyone chose — the claim-based lease underneath is already safe for multiple concurrent workers. Fixing them is one piece of work, not two: replace the single-set gate with a real concurrency budget and enforce that same budget fleet-wide.

  • No backpressure. A burst of intake items produces more chains rather than throttling.

  • No systematic retry/backoff policy — retry behaviour is per-lane and ad hoc.

Recommendation

  1. Load-test the Neon connection pool under concurrent drain activity plus storefront traffic. This is the client's own untested item #1 and the highest-value test available. Confirm the pooled DATABASE_URL carries the correct Prisma/pgbouncer parameters and a sane connection_limit for the lambda count.
  2. Instrument the queue — emit depth and oldest-lease-age per lane, and alert on both. Cheap, and it converts an invisible failure mode into a visible one (pairs with wiring ERROR_WEBHOOK_URL).
  3. Bound total in-flight drain chains globally, and add jitter to the per-minute crons.
  4. Add a staleness gate to the catalog fail-open so a snapshot older than N hours raises an alarm instead of serving silently — this is the specific fix that makes bottleneck #1 detectable.
  5. Do not replace the queue as a launch task. The Postgres-lease pattern is sound and well-documented. The gaps are observability and global bounding, which are far cheaper to close than a migration to Inngest/QStash. Revisit a managed queue only if the number of lanes grows or the self-kick/loop-detector tension recurs.

Size 90,690,773 bytes ≈ 86.5 MB (lib/board/matting/model.ts)

The sharpest technical finding: the WASM fallback is permanently single-threaded.

ort.env.wasm.numThreads = scope.crossOriginIsolated
  ? Math.min(4, scope.navigator.hardwareConcurrency || 1)
  : 1; // no COOP/COEP on this site — explicit, so ort doesn't warn-and-guess

There are no COOP/COEP headers anywhere in the application, so crossOriginIsolated is always false and the branch always resolves to 1 thread. This is not an oversight that can simply be fixed: enabling Cross-Origin-Embedder-Policy would break the site's third-party embed strategy — Tolstoy, Judge.me, Kiwi Sizing, GTM, GA4 and the TikTok pixel (docs/integrations.md) would each need to serve CORP/CORS headers. Single-thread WASM is locked in by a different product decision. So on any device without WebGPU, a U²-Net variant runs at 1024×1024 on one WASM thread.

Three concrete risks

  1. Memory — the worst failure mode is uncatchable. 86.5 MB of weights plus a 12.6 MB input tensor plus ISNet activations at 1024². On mobile Safari, exceeding the per-tab limit kills the tab outright — no JavaScript error, so the worker's try/catch and its "quiet revert" cannot catch it. The shopper simply loses the page and their board state.
  2. Latency on the WASM path. Single-threaded WASM inference on this model class is order-of-tens-of-seconds on mid-range mobile hardware. There is no timeout and no "this device can't do this" message — the user waits.
  3. Repeat downloads on iOS. The worker caches weights in CacheStorage ("second session = no refetch"), which is correct. But Safari evicts script-writable storage under pressure and under ITP policy, so the 86.5 MB fetch may recur for iOS shoppers — on cellular, unprompted.

WebGPU coverage is good on current Chrome/Edge desktop, Chrome Android, and Safari 26+/iOS 26+, but absent on older iOS. Devices on older iOS take the single-thread WASM path by definition, and budget Android devices may report WebGPU while having a GPU that performs no better.

What the implementation gets right — and why the exposure is narrower than it appears

This is careful work, and the mitigations are real:

  • Lazy — nothing loads until the first "cut it out"; no cost to shoppers who never use it
  • Dedicated worker — the main thread never blocks, so the page stays responsive
  • Honest progress — "sharpening the scissors — 12 of 86mb"; the download is not hidden
  • sha256 integrity check on the weights, with poisoned-cache deletion on mismatch
  • Serialized — one cut at a time, so no concurrent inference pile-up
  • Graceful failure — errors surface in the control's own text and quietly revert
  • Privacy — photo pixels never leave the device for matting
  • Server-side reuse for product pieces (the important one). cutOutPiece does a pre-flight pieceCutLookup; a catalog image cut by any user on any board is stored under a source-keyed shared path and reused by everyone thereafter — "first cut wins."

That last point materially changes the risk profile. The common path — cutting a catalog product — usually skips the model entirely after the first user anywhere has cut that product. The genuinely exposed path is cutOutPhoto: a shopper's own uploaded photo, which is unique by definition, always runs locally at full cost.

Assessment. This is a feature-quality risk on a secondary surface, not a correctness or security risk, and it cannot affect the storefront or checkout. But it will produce a poor experience on a meaningful share of mobile devices, and its worst failure mode is a silent tab kill that the existing error handling cannot report — which, combined with F-10, means the team would have no signal that it is happening.

Recommendation, cheapest first

  1. Add a capability gate before offering the verb. Probe navigator.gpu and navigator.deviceMemory; where WebGPU is absent and memory is low, either hide the scissors or present it with an honest "this may take a while on this device" and an explicit confirm. Hours of work; removes the worst outcomes.
  2. Warm the piece cache. Pre-cut the top-N catalog images server-side (sharp is already in the trace for /api/board/cut) so the shared cache is populated before shoppers arrive. This converts the common path to a pure download-free lookup.
  3. Instrument it — emit an event on cut start / success / failure with the chosen execution provider. Currently there is no way to know how often this path fails in the field.
  4. Move matting server-side entirely — see the addendum below. On analysis this is the correct end state, not merely a fallback.

F-13 addendum · Should matting move fully server-side? Yes — and the current design already concedes the argument

The decisive fact: the raw photo is already uploaded to the server before any cutting happens.

The actual sequence today:

  1. uploadPhoto() (lib/board/photo-client.ts:58) downscales in-canvas to a ≤2200 px JPEG and POSTs it to /api/board/photo.
  2. The server sniffs the type, rotates-then-strips EXIF, re-encodes via sharp, writes full + 480 px thumb to Blob at boards/photos/{rid}/{hash}, and records an audit row.
  3. The client receives durable URLs and only then creates the board element.
  4. "cut it out" → runCutPipeline fetches that server-hosted rendition back down (fetcher(src)).
  5. The worker downloads 86.5 MB of weights.
  6. Inference runs on WebGPU or — on any device without it — single-threaded WASM.
  7. The cutout is uploaded back through the same /api/board/photo door.

The worker's header comment — "Photo pixels never leave the machine here" — is accurate about that worker only. The pixels left the device one step earlier, and step 4 re-downloads them from the server in order to matte them locally.

So the privacy rationale for client-side matting is already void. What remains is four network round trips including an 86.5 MB model download, to avoid inference on an image that is already sitting in the client's own Blob store.

Server-side collapses steps 3–7 into: upload → matte → return both renditions. Fewer round trips, ~86 MB less transfer per new device, and zero device variance.

Critical qualifier: server-side, but not on Vercel functions. The original client-side choice was reasonable given the platform:

  • 86.5 MB cannot be bundled — the project already fights function-size limits (a 50 MB gate is documented for the looks routes in next.config.ts).
  • It would have to be runtime-fetched to /tmp — precisely the ffmpeg pattern, inheriting all of F-06's fragility.
  • Every cold start would re-fetch 86.5 MB and re-initialise an ORT session.
  • Roughly 1–2 GB of memory per concurrent inference.

On a persistent container every one of those inverts: the model loads once at startup and stays warm; onnxruntime-node is already a devDependency; real multithreading applies because the COOP/COEP constraint does not exist server-side; inference lands in the ~1–2 s range instead of tens of seconds; failures flow through the existing monitoring seam instead of dying invisibly; and a model swap becomes a deploy rather than a client cache-invalidation dance with -vN pathnames.

This is the second workload arguing for the hybrid container lane — and a stronger example than video, because it is shopper-facing latency rather than background batch.

A container is not the only route — PhotoRoom is already integrated and funded, and routing board cuts through it removes the 86.5 MB download and all device variance with no new estate. And §10 now costs the hybrid at 12–20 engineer-days ≈ 2–3 weeks, so the container option is cheaper than earlier drafts implied. Both paths still require F-14 to close first — either one turns an unauthenticated public endpoint into an expensive one.

Two design notes

  1. Different latency profile from the video lane. Video finishing is background batch, where minute-scale queue pickup is fine. Matting is interactive — a shopper is waiting. This wants a synchronous call to a warm service, not SQS with minute-scale pickup. Same container, different entry point.
  2. Instant re-cut is preserved. Both renditions already persist server-side, so if (cur.cutSrc) return s.setCut(uid, true) keeps working unchanged.

Cost shifts from the shopper's device to the client, but modestly: the source-keyed piece cache already dedupes catalog cuts, so the marginal volume is user-uploaded photos only, at ~1–2 s of warm CPU each.

Prerequisite: close F-14 first. Putting ML inference behind an unauthenticated, unrated-limited public endpoint would be a denial-of-service invitation.

F-17

The admin session token is a non-revocable bearer credential derived from the shared password, and the login endpoint has no rate limit

HIGHVERIFIED+

F-05 established that the back office is guarded by one shared password. This finding is about the mechanics of that credential, which are weaker than the shared-secret problem alone implies.

lib/merch/auth.ts is 21 lines:

export async function sessionToken(password: string): Promise<string> {
  const data = new TextEncoder().encode(`society-admin:${password}`);
  const digest = await crypto.subtle.digest("SHA-256", data);
  return /* hex */;
}
export function isAdminRequest(i): boolean {
  if (!i.expectedToken) return false;                 // fails closed when env unset ✓
  return i.cookieToken === i.expectedToken || i.headerToken === i.expectedToken;
}

Four consequences follow from the token being a pure function of the password:

  1. It is the same value for every admin, every device and every session, permanently. There is no server-side session record, so no individual session can be revoked. The only revocation available is rotating ADMIN_PASSWORD, which signs everyone out simultaneously. The cookie's 30-day maxAge is client-side only — a copied token stays valid indefinitely.
  2. It is a bearer token, not just a cookie. isAdminRequest accepts the value in the x-internal-auth header as an alternative to the cookie, because the app uses that header for its own self-calls. Anything that captures the value once — a log line, an intermediate proxy, a screenshot of devtools, a browser extension — grants full back-office access until the password is changed. There is no binding to IP, user-agent or session.
  3. A captured token permits offline recovery of ADMIN_PASSWORD itself. The digest is unsalted, single-round SHA-256 over a known-prefix string. For a human-chosen password that is GPU-fast. If the password is reused anywhere else, the blast radius extends past this application.
  4. /api/merch/auth is the only unauthenticated door inside the middleware matcher, and it is not rate limited. Its sole friction is: 
    if (!expected || password !== expected) {
  await new Promise((r) => setTimeout(r, 500)); // brute-force friction
  return NextResponse.json({ error: "wrong password" }, { status: 401 });
}
    That delay is per-request and in-process. It does not throttle by IP and does not count attempts, so parallel connections defeat it completely. lib/abuse/rate-limit.ts exists and is wired to three routes (F-14) — the admin login is not one of them. A single human-chosen password protecting the entire back office, with effectively unlimited guessing, is the weakest link in the authentication design.

What is correctly done here, and should not be lost in remediation: the cookie is httpOnly, secure in production, sameSite: "lax" (which blocks cross-site POST and therefore covers the CSRF case for state-changing admin calls without a token), scoped to path: "/", and isAdminRequest fails closed when ADMIN_PASSWORD is unset in production while staying open in local development. proxy.ts documents its own public-prefix exemptions and explains why the /api/shopify/webhooks entry is not load-bearing today. The plain !== comparison is not constant-time, but that is not practically exploitable over HTTP for this token and is not worth spending remediation budget on.

Recommendation, in order.

  1. Rate-limit and lock out /api/merch/auth keyed by IP. This is a one-line application of the limiter that already exists, and it removes the brute-force path today.
  2. Stop accepting the admin token in a request header for anything but the internal self-call path, or give the internal path its own distinct secret. Today one value serves both purposes, which is what makes leakage catastrophic.
  3. Replace the derived token with real sessions: a random 256-bit session id, a server-side session row, per-user identity, idle plus absolute expiry, and individual revocation. This is the same change F-05 asks for and should be done once, together with accounts and roles.

  1. The documented production workflow is exactly the broken one. package.json defines "db:deploy": "cp .env.local .env && (prisma migrate deploy; …)".   3. This makes F-04 concrete rather than theoretical. F-04 noted that no restore has been drilled. This is why that matters: schema-first recovery does not work today. A Neon PITR restore of an existing branch would be fine; provisioning a clean database from source would not.

    CREATE UNIQUE INDEX "Event_purchase_order_key" ON "Event" ((meta->>'orderId'))
  WHERE type = 'purchase';

    This is the duplicate-purchase-event guard. It is a partial expression index, which schema.prisma cannot express — so after db push the Event table carries only its five declared indexes and this one does not exist (verified directly against pg_indexes). Any environment provisioned the only way that currently works is missing purchase idempotency. The team knows the index is fragile — a later migration carries the comment "Event_purchase_order_key must never appear in a generated cleanup" — but nothing enforces it.

    Scope, stated fairly: this is the only non-schema-representable object in the entire migration history. A sweep for expression indexes, partial indexes, extensions, triggers, functions and views found nothing else. One index, not a systemic problem — but the wrong one to lose.

  5. The checklist's migration count is wrong — it says 27, there are 50. Consistent with F-09.

Recommendation

  1. Squash the history into a baseline. Generate one migration from the current schema (prisma migrate diff --from-empty --to-schema-datamodel), append the raw-SQL index to it, and mark it applied on production with prisma migrate resolve --applied. This makes migrate deploy work on a fresh database, which is the whole point of keeping migrations.
  2. Add the raw-SQL index to that baseline explicitly, with a comment explaining that schema.prisma cannot represent it.
  3. Prove it in CI (F-01): spin up a throwaway Postgres, run migrate deploy from empty, assert exit 0. That single job would have caught this, and it prevents recurrence permanently.
  4. Correct the checklist's count and state which command actually provisions a new database.

Paths no longer tracked at HEAD 0.08 GiB — only 2% of history
Paths still tracked at HEAD 4.23 GiB — 98%

So deleted files account for almost nothing. The dead weight — about 2.5 GiB — is previous versions of images that are still in the tree, rewritten in place during creative iteration. The look heroes are the clearest case: looks/l-spritz.jpg has 12 committed versions, l-cafe.jpg 11, l-night-garden.jpg 10. The June 2026 colorway recolor (737 images) and the June 2026 model recast each rewrote large sets wholesale. Every iteration stored a complete new copy.

The cost is already being paid — three times, documented in their own config

next.config.ts records three production deploy failures caused directly by this tree:

  • /look/* OG image — a dynamic fs path made output-file tracing over-approximate to all of public/images (2.24 GB), which "blew the 250 MB function limit and failed the deploy"; 4,943 files leaked into the bundle pre-fix.
  • Looks Creator — "packaged at 2.62GB on July 2026, same failure class."
  • The music shelf — "traced to 2.84GB (all of public/images + scripts + docs) on the first deploy" (July 2026).

A substantial share of that 250-line config — which this assessment credits elsewhere as an exemplary incident ledger — exists to work around binaries in the repository. And confirmed by grep: no deployed function fs-reads public/images at all. The config says as much — "Deployed functions NEVER fs-read public/ (flats fetch off the CDN)". The tree is needed only for static serving.

The inversion worth naming

Git currently preserves ≈2.5 GiB of regenerable derivatives — recolors, recasts, re-rendered look heroes, all reproducible from source and vendor APIs — while the irreplaceable source it should be protecting (the manufacturer .xlsx master lists, the supplier intake sheets, the product-export CSV) is in no backup we can see and sits on one laptop (F-03). That is exactly backwards.

Recommendations, in order

  1. Finish the migration already underway — this is the primary answer, and it is not a git tool. The architecture already has the right destination: catalog-images.generated.ts maps the real launch line to re-hosted Shopify CDN URLs, BLOB_BASE is Vercel Blob, and functions already never read public/. The committed tree is the prototype-era file-drop convention (prod_<cat>_<id>_<color>.jpg) that the newer CDN-backed design superseded but never cleaned up. Serve all imagery from Blob/CDN and delete the tree. Dependency: this needs the 69 PRODUCTS importers swept first (F-16, F-24, plan item 3.2) because the prototype line is still load-bearing. It also makes F-20's next/image adoption cleaner, since remotePatterns for those hosts is required either way.
  2. Do not reach for Git LFS as the fix. It is the reflexive recommendation and it is a poor fit here: it does not shrink existing history (a rewrite is still required), it adds storage and bandwidth cost plus a CI checkout step, and — decisively — it does not help the deploy problem at all, because LFS still materialises real files into the working tree at build time, so output-file tracing behaves identically. LFS solves clone size for repositories that must keep binaries. This repository should not keep them.
  3. Then rewrite history once with git filter-repo, reclaiming ≈2.5 GiB. The usual objection is that rewriting invalidates documented commit references — checked, and it is a small cost here: only 2 commit SHAs across the handover, the execution plan, next.config.ts and finish.ts resolve to real commits. Do it in a single pass after the images leave, not before.
  4. Available today at zero cost, while the above is pending: git clone --filter=blob:none (partial clone) or --depth for new contributors and CI checkouts. For a solo operator plus agents this is likely sufficient interim relief and needs no decision from anyone.
  5. Adopt a policy, because the distinction is what went wrong. Generated binaries — renders, recolors, look heroes, contact sheets — are reproducible artifacts and belong in Blob, never in git. Source binaries — the manufacturer spreadsheets — belong in versioned object storage with a manifest committed to git. Today the repository does the opposite of both.

Recommendation, cheapest first. (1) Measure one real shop grid and one PDP with browser devtools or Lighthouse — this converts the finding from a payload inventory into a page-weight number, and it is roughly an hour of work. (2) Adopt next/image on the grid and PDP surfaces first, with remotePatterns for Blob and the Shopify CDN; this is where the return is concentrated. (3) Add width/height to the 82 tags as they are migrated, for layout stability. (4) Separately, consider whether 2.24 GB of imagery belongs in git at all — it is the main reason .git is 4.2 GB, and it lengthens clone, CI checkout and build for every future contributor.

  db.event.deleteMany({ where: { customerId: gid } }),
  db.customer.delete({ where: { id: gid } }),

Two tables, plus a best-effort avatar Blob delete. Verified by grep, the following have zero delete sites anywhere in the codebase: ContactCapture (email + phone), TasteCapture (email + taste profile), FitCard, GeneratedLook, MktSession, StylistSession. Board and BoardUpload each have exactly one delete site — the shopper's own "toss this board" and the admin's block verb, neither of which is reachable from account deletion.

So a shopper who signs in, enters her email at the try-on gate, completes the quiz, uploads photos to a board, and then deletes her account leaves her email address in two tables, her phone number in one, and her uploaded photographs in Blob and Postgres. The route returns { ok: true }.

The Shopify redaction webhooks are absent

lib/shopify/webhooks.ts handles products/create|update|delete, collections/*, orders/create|updated and inventory_levels/update. It does not handle:

  • customers/redact — Shopify's instruction to erase a specific customer's data
  • customers/data_request — a subject-access request
  • shop/redact — erase all shop data after uninstall

These are the compliance webhooks for a Shopify integration handling customer data, and the store is the system of record for identity here (F-15 tier 1). A erasure request that arrives through Shopify today silently does nothing in Neon. The SyncRun audit row would not even record a miss, because the topic falls through the switch entirely.

What is done well, and why it makes the gap conspicuous

The try-on avatar path is a model implementation and should be preserved verbatim as the pattern for everything else:

  • Anonymous shoppers never persist an image at all — the person photo stays an in-memory data URL in useTryOn. No Blob, no row. This is the strongest privacy property in the system.
  • A signed-in shopper must take an explicit consent action; the Blob path is keyed by customer gid and overwrites the same object, so re-saves cannot orphan images.
  • Revoke is total — it deletes the Blob, clears avatarBlobUrl, and sets tryOnConsent false.
  • Account deletion cascades to the Blob.
  • The stated policy is written at the top of lib/account/avatar.ts: "only the uploader's own image; no retention beyond session without consent."

That is a correct, deliberate, defensible design for the most sensitive item in the system. The finding is that it was never generalised. Board photo uploads — also images of real people, uploaded by anonymous users with no account — get none of it: no consent action, no revoke, no deletion path, no retention limit, and (F-14) no moderation.

Two further controls verified as correct: email and phone are SHA-256 normalised before transmission to Meta and TikTok CAPI ("RAW — hashed here, never stored raw", with per-platform phone normalisation), and the Klaviyo integration uses the subscribe endpoint with an explicit consent: "SUBSCRIBED" rather than a bare profile create. Also checked and clean: no PII appears in any of the 293 log call sites (F-10) — a good result that was not guaranteed.

Qualification added July 2026 (A-01). The CAPI hashing control above is confirmed and is not withdrawn — the values are SHA-256 normalised and never stored raw. But the measurement review established that the identifiers are transmitted without any reference to the shopper's consent choice: soc_consent is read at exactly one site in the codebase, the client component, and the server relay in lib/marketing/order-attribution.ts never consults it. So a shopper who chose "Essential only" still has their hashed email and phone sent to Meta and TikTok on purchase. Hashing reduces exposure in transit; it does not supply a lawful basis, and a SHA-256 of a normalised email is precisely the join key the platforms use to identify a person. This is the same defect shape as the ContactCapture inconsistency below — consent asserted to a third party without a local record — and recommendation 3 should be read as covering OrderAttribution too.

One inconsistency inside that otherwise-correct picture: TasteCapture records consentMarketing and consentSource, but ContactCapture has no consent column at all while still carrying klaviyoPushed. The try-on gate treats email as "the capture gate's only mandatory field." So marketing consent is asserted to Klaviyo without being recorded locally, which means the basis cannot be evidenced later from the client's own data.

Recommendation, in order

  1. Extend the deletion cascade to all nine stores in the existing transaction, keyed by both the customer gid and any session ids merged into that account. This is the single highest-value fix and it is contained — deleteAccount is a two-line function today.
  2. Handle customers/redact, customers/data_request and shop/redact in the existing webhook switch. The HMAC verification, the always-200 posture and the SyncRun audit row are already built; these are three new case blocks calling the cascade from step 1.
  3. Record consent on ContactCapture as TasteCapture already does, so the Klaviyo assertion is backed by a local record.
  4. Generalise the avatar pattern to board uploads — consent action, revoke, cascade — or decide deliberately that anonymous board photos are out of scope and document why.
  5. Confirm whether Blob objects are reaped when their owning row is deleted. User photos live at the deterministic path boards/photos/{sessionId}/{sha256}.webp with access: "public" and addRandomSuffix: false. The path is not practically enumerable — it requires both a high-entropy session id and the exact image bytes — but the URL is permanent, unauthenticated, and survives row deletion unless explicitly deleted. Vercel Blob is public-only, so the mitigation is reaping, not access control.

One question for the client, not a finding. There is no age gate anywhere — no date of birth, no over-18 assertion, no minimum-age attestation on the newsletter, quiz, contact gate or photo upload. The brand's own mood vocabulary (dorm, tennis) suggests a young demographic, and the system collects email, body sizing and photographs. Whether that requires an age gate is a legal determination rather than an engineering one, and it should be put to counsel before launch.

The nightly Shopify reconcile is a single-pass 300-second walk with no resumption

MEDIUMVERIFIED+

What is sound, and should be credited first. The Shopify↔︎Neon mirror uses the right dual-path design: HMAC webhooks for near-real-time updates plus a nightly full reconcile to heal drift. The reconcile is non-destructive — per-product upserts through the same mappers as the webhook path, never a wipe-and-reload — so there is no window in which the storefront reads an empty mirror. It calls warmDb() first. It records every run in SyncRun. This is better than most mirrors.

The ceiling. app/api/cron/shopify-reconcile/route.ts:20 declares maxDuration = 300, and lib/shopify/reconcile.ts:276-391 is one sequential pass: cursor-walk products → per-node upsertProduct → walk the mirror for deletions → repeat for collections. Comfortable at the current ~1,400–1,500 products. The pressure arrives with catalog growth, and it arrives as silent incompleteness — a truncated reconcile heals a prefix of the catalog and leaves the tail drifted, with the same SyncRun row shape as a successful one.

The pattern to apply already exists in this repository. intake-drain, looks-drain and creative-drain all implement bounded-work-plus-self-kick with a lease. The reconcile is the one long-running job that does not use it.

Two smaller points from the same finding. Sync history is visible only by opening the admin SyncPanel (last 10 runs) — nothing alerts on a rising error rate or a truncated pass; this is F-10's missing transport again, and it is the reason the failure mode above would be silent. The claim that the inventory-webhook stub causes ~24 h stale stock is a false positive under House Law L1; see F-15's "one thing I checked and cleared".

Recommendation. Chunk the reconcile with a persisted cursor and self-continuation, matching the existing drains. Not urgent at today's catalog size; sequence it with the growth that makes it necessary, and add the alert now because that costs nothing once F-10's transport is wired.

4d. How the catalog data tier got its shape — the chronology

This section exists because F-15, F-16 and F-24 read as questionable architecture and are better understood as an unfinished internal migration. The distinction changes what to do about them, and it materially changes the conversation with the client. Established from git history and the client's own §13.

The sequence

Date Event
May 2026 → 06-10 lib/catalog.ts holds a hardcoded TypeScript product array. The PoC-era doc describes the app as "front-end only — no backend, no real payments; commerce is simulated and persisted to localStorage."
June 2026 The entire commerce backend lands in a single day — lib/shopify/{client,mirror,webhooks,reconcile,migrate-plan}.ts, scripts/migrate-catalog-to-shopify.ts, lib/catalog-static.ts (the old array preserved as a named export), and the build-time bake (generate-catalog-base.ts + catalog.generated.ts)

Two things this corrects

The hardcoded catalog went into Shopify, not into Neon. migrate-catalog-to-shopify.ts "seeds the SOCIETY Shopify store from the static catalog truth" — 1,351 products via productSet, inventory via inventorySetQuantities, 23 collections. It executed: catalog-images.generated.ts records that "the load handed Shopify each supplier photo; Shopify re-hosted it under cdn.shopify.com." Neon has only ever held a mirror. There was never a moment when Neon was a second master. Shopify has been the system of record since the day a backend existed, which is the correct call and should be credited as such.

The live-data path was not a later addition. Webhooks, mirror and nightly reconcile shipped on June 2026, the same day as the bake. There was no phase of holding a catalog in a database without syncing it from Shopify. The two tiers were designed and shipped together, exactly as §13 documents:

What is actually unfinished

Not the Shopify integration — that is complete and functioning. What is incomplete is the app-side read migration onto catalog-live.ts:

  • 57 modules use the runtime seam; 69 still import the build-time snapshot.
  • The primary shopper surfaces — home, /shop, PDP, sitemap — are correctly on the runtime seam.
  • What remains stranded is mostly admin surfaces, plus the /looks module and the quiz.

The June 11 bake was a compatibility shim: rather than rewrite ~120 import sites the day the backend arrived, they made the database emit the shape the PoC already consumed. That is a defensible engineering decision under time pressure. The proper seam followed five days later. The shim was never retired.

Why the framing matters

F-16 and F-24 are consequences of the unretired shim, not of a bad design:

  • The snapshot is stale and describes the archived prototype line (F-16) because nothing forces it to be regenerated — the gate exists and is off.
  • The snapshot reaches the browser (F-24) because Client Components sit among the 69 importers. Nothing in the documented design requires a server-side fail-open floor to ship to clients; the import graph causes it.

The fail-open floor itself is legitimate and should be kept. Neon auto-suspends, the architecture is deliberately fail-open throughout, and a last-known-good snapshot means a database blip degrades freshness rather than emptying a fashion storefront. The correct outcome is a server-side floor that is regenerated every build and never crosses into a client bundle — not the removal of the floor.

One distinction that does not get the same defence

F-15's taxonomy tier is a different case, and a weaker one. catalog.generated.ts is a cache of data that lives in Postgres and has a working runtime equivalent. The taxonomy files — garment facets, pattern tags, colour tags, from July 2026 onward — are primary data that never had a database home at all. They are the output of AI vision passes plus founder rulings, they exist only as committed TypeScript, and the derive layers (lib/garment-facets.ts, lib/patterns.ts) contain no query path. There is nothing in the database to read.

So the two halves need different remedies: the catalog is a sweep (finish migrating the 69 importers), while the taxonomy is a data-modelling project (give it a home in Postgres first). Plan items 3.1 and 3.2 reflect exactly that split.

5. What is working well

These are genuine strengths and should be preserved through any remediation.

  • Clean typecheck across ~1,400 source files, and ~8,030 passing tests.
  • The database layer is in good shape. 159 indexes across 64 tables, no missing-index catastrophe, no N+1 pattern anywhere on a shopper request path, and raw SQL correctly parameterised at all 9 sites (§4c). For a schema this size, grown this fast, that is a better result than expected.
  • Server/client separation holds where it matters most. Prisma appears in zero client chunks, enforced by a deliberately hand-rolled server-only guard written because the canonical one is unresolvable under this repo's test setup (F-24).
  • Fail-open shopper path by design. Live reads floor to a build-time catalog snapshot (lib/*.generated.ts); a dead database degrades freshness but cannot blank the store. Third-party embeds are no-ops until their env key exists. Telemetry never throws.
  • Fail-closed money paths. Paid generation is gated before spend by kill-switches and caps; admin auth fails closed in production; webhooks verify HMAC before anything else.
  • Payments are correctly and completely delegated to Shopify. No payment code, no payment SDK in the dependency tree, and a guard test that pins this. /api/checkout returns only a Shopify-minted checkoutUrl.
  • The manual-upload lane never forks commerce truth. Supplier spreadsheets stage into Neon and can only reach shoppers by way of a Shopify DRAFT that a human promotes to ACTIVE. Uploads bypass the serverless body limit correctly (direct-to-Blob with an admin-gated token), three supplier formats are auto-detected, and the publish boundary carries a hard taxonomy invariant (F-15).
  • The try-on avatar privacy design is exemplary and should be the template for every other personal-data path. Anonymous shoppers never persist an image at all — it stays an in-memory data URL. Persistence requires sign-in plus an explicit consent action; the Blob is keyed by customer gid so re-saves cannot orphan images; revoke is total (Blob deleted, field cleared, consent withdrawn); account deletion cascades to the Blob. The policy is stated in the module header and actually enforced by the code beneath it (F-21).
  • Third-party PII handling is correct. Email and phone are SHA-256 normalised before transmission to Meta and TikTok CAPI, with per-platform phone normalisation, and never stored raw. Klaviyo uses the subscribe endpoint with explicit consent rather than a bare profile create.
  • No PII in the logs. Despite 293 ad-hoc log call sites (F-10), none emits an email address, phone number or customer identifier. The session module also documents that token strings are never logged. That is discipline, not luck.
  • Customer authentication is properly built. Real Shopify OAuth via the Customer Account API, an AES-GCM sealed session cookie with context binding (authenticated encryption, not merely signing), mandatory refresh-token rotation, an in-flight dedup map that prevents the single-use refresh-token race from causing silent logout loops, and a documented rule that token strings are never logged. httpOnly + secure + sameSite: lax. This is the strongest part of the auth surface and is markedly better than the admin side (F-17).
  • Defense in depth on the admin API. 86 of the 92 routes behind the middleware gate re-check authorization inside the handler, so a matcher misconfiguration does not open them. All 15 intake routes self-guard despite sitting outside the matcher entirely.
  • Money-safety gates precede spend on public endpoints. /api/tryon/render and /api/screenshot/match are unauthenticated by necessity but check a per-identity tier cap and a global ceiling before the paid call, and record only genuine cache-miss renders. That is the right pattern; the finding in F-14 is that three sibling endpoints do not follow it.
  • Object-level authorization is enforced, not assumed. Board read/update/delete and print generation are all owner-scoped by session, with a stranger's id returning 404 and a compare-and-set on updatedAt to prevent cross-tab clobbering.
  • Deliberate scoping is documented rather than accidental. The inventory_levels/update webhook is a knowing no-op because House Law L1 means quantity is never displayed — the decision, its reason and its enforcement points are all written down. Several apparent gaps in this system are of this kind and check out on inspection.
  • Exceptional incident documentation. next.config.ts and finish.ts record root causes with dates and deployment IDs. This is rare and valuable — it should be converted into automated checks rather than left as prose.
  • A prior adversarial readiness review was commissioned and acted on. The team is not unaware of its gaps.
